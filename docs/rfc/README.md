# Requests for Comments

RFCs preserve substantial proposals that may shape Jarling later. They do not
describe released behavior and are not implementation plans unless explicitly
accepted and scheduled.

## Status values

- **Draft**: exploratory and open to change.
- **Under Review**: actively being evaluated.
- **Accepted**: approved for implementation but not necessarily delivered.
- **Rejected**: deliberately not being pursued.
- **Implemented**: delivered; current behavior has been moved to canonical
  `user/` and `technical/` documentation.
- **Superseded**: replaced by a linked RFC.

An RFC should define the problem, motivation, proposal, alternatives, expected
impact, risks, phases, and exit criteria. If implemented, update its status and
move the resulting behavior into the present-tense documentation. Create or
update RFCs only during an explicitly requested documentation or proposal task.
